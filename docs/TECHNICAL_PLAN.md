# Play Holiday 小程序技术方案

## 1. 技术边界

- 客户端：Taro 4.2、React 18、TypeScript、Less。
- 首发端：微信小程序；不以 H5 兼容牺牲地图和原生交互。
- 地图：Taro `Map` 映射微信地图组件；公开地图点和私人点使用不同数据源。
- 状态：M1–M3 先用 React 局部状态与 `Taro.setStorage`；接后端时再引入服务器状态层，不提前增加全局状态库。
- 服务层：页面不直接拼接生产接口，统一通过 `src/services` 与 `src/api`。

## 2. 页面与分包

主包只保留四个高频 Tab 和首屏所需代码：

- `pages/index/index`：出钓首页；
- `pages/map/index`：地图；
- `pages/record/index`：记录入口；
- `pages/mine/index`：我的。

水域详情、趟次编辑、识鱼和规则原文在功能增长后进入分包，降低启动体积。Tab 页使用微信原生 TabBar，避免自定义导航的状态同步与无障碍成本。

## 3. 数据分层

```text
权威规则／天气水文 ──> 运营核实层 ──> 公开水域卡
地图服务商 POI ─────> 来源标记层 ──> 钓场／钓具店
用户精准坐标 ───────> 本地私人层 ──> 私人点／私人日志
用户主动贡献 ───────> 客户端脱敏 ──> 水域级匿名趟次
```

禁止把用户原始精准坐标先上传服务器、再在服务端脱敏。公共趟次只接受既有 `water_body_id` 或运营定义的粗粒度区域。

## 4. UI 工程约束

- 设计 token 以 `design-system/play-holiday/MASTER.md` 为唯一来源。
- 使用 750 设计宽度下的 8pt 节奏；关键触控目标最小 96rpx（约 48px）。
- 地图原生组件上方覆盖交互使用 `CoverView`；复杂列表与表单不要强行叠在地图原生层上。
- 一屏只保留一个主 CTA；风险状态由图形／文字／颜色共同表达。
- Tab 图标和地图标记使用同一套 2px 圆角线性图标，不用 emoji 充当结构图标。

## 5. 本地存储键

- `ph.trip.drafts.v1`：趟次草稿与离线队列；
- `ph.private.spots.v1`：私人点；
- `ph.favorites.v1`：收藏水域；
- `ph.map.last-filter.v1`：地图筛选；
- `ph.onboarding.v1`：隐私与贡献说明完成状态。
- `ph.external.clues.v1`：外部公开内容的待审核线索；不得写入趟次统计。
- `ph.place.updates.v1`：用户对地点追加的事实更新；按时间形成新版本，不覆盖初始收录数据。

所有存储结构带版本号。后续迁移必须保留失败回滚，不能静默清空用户私人记录。

## 6. 质量闸门

- 每个里程碑：TypeScript 检查、`pnpm build:weapp`、开发者工具运行、至少一次真机触控检查。
- 地图、定位、天气、识鱼、上传分别有错误与降级状态。
- 上线前移除生产环境调试面板；请求域名、隐私声明和微信后台权限配置一致。
- 生产数据接入前完成首批水域规则复核和敏感水域隐藏开关。
