# Play Holiday 小程序开发里程碑

> 原则：每个里程碑都交付可在微信开发者工具打开的版本；先用可追溯的模拟数据验证交互，再接生产数据。完成标准包含构建、关键状态和真机触控检查，不以“页面写完”代替验收。

## M0：产品与工程基线

- PRD v1.1：合法城市／郊区湖库台钓，排除首轮两江干流与保护区。
- UI/UX：由 `ui-ux-pro-max` 生成并经移动端规则校正的设计系统；Anthropic `frontend-design` 做视觉独特性复核。
- 技术：Taro 4.2 + React 18 + TypeScript + Less，微信小程序为唯一首发端。
- 交付物：`docs/PRD.md`、`docs/TECHNICAL_PLAN.md`、`design-system/play-holiday/MASTER.md`。

完成标准：产品边界、页面结构、数据分层、隐私边界和里程碑验收口径一致。

## M1：可运行的出钓决策骨架

- 四栏原生导航：出钓、地图、记录、我的。
- 首页：今日天气摘要、风险提示、近期水域卡、明确的“记一趟”主动作。
- 地图：武汉中心、模拟水域标记、状态筛选、点选水域、用户主动定位。
- 记录与我的：保留可继续扩展的入口和本地状态骨架。

完成标准：`pnpm build:weapp` 通过；375px 视口无横向溢出；所有主触控目标不小于 48px；拒绝定位仍可浏览武汉数据。

## M2：水域可信详情

- 水域详情、来源与复核时间。
- 水域状态与钓法／杆数／钩数／饵料／装备约束分开展示。
- 收藏、导航、查看规则原文、纠错与高风险热度抑制。

完成标准：禁止、条件允许、待核实不只靠颜色区分；样本不足不展示百分比；规则冲突走保守状态。

## M3：10 秒趟次与私人位置

- 空军／有口／爆护三选一，现场状态渐进展开。
- 私人记录与匿名水域贡献清晰分流。
- 本地离线队列、幂等 ID、重试和删除。
- 私人点默认本地；公开贡献只上传水域 ID 或粗粒度区域。

完成标准：主流程中位完成时长约 10 秒；断网、杀进程和重复点击不丢失或重复提交。

## M4：识鱼与私人日志

- 迁移现有拍照识鱼能力到记录链路。
- 1–3 个候选、置信提示、人工纠正和“不确定鱼种”。
- 识别失败仍可保存照片和趟次；日志支持基础复盘。

完成标准：低置信结果不包装成确定结论；识鱼服务不可用不阻塞日志保存。

## M5：真实数据与灰度

- 接入地图 POI、武汉逐时天气、权威天气／水文预警和规则来源。
- 后端、登录、匿名聚合、审核、埋点与内容安全。
- 2–3 个核心水域，每水域 6–8 名种子用户灰度。

完成标准：隐私与安全清单通过；第 14／30 天实验可区分信息价值、数据密度和贡献意愿，不能把人工供给当成自持飞轮。

## 武汉试点退出条件

武汉是首个验证单元，不是长期地域边界。进入下一城市前至少满足：

- 武汉初始地点基线可用，且用户更新以追加记录方式形成新版本；
- 至少 2–3 个核心水域能够持续产生真实用户更新，而非只依赖一次性导入；
- 地点过期、关闭、规则变化和位置纠错都有可用闭环；
- 数据结构、采集器和展示层不依赖武汉专有 ID，可通过城市配置复制。
